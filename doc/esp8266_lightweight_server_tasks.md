# ESP8266 轻量服务器角色与任务清单

本文档罗列：在 **Station 模式** 连入路由器后，ESP8266 作为 **轻量 Web 服务 + 串口桥** 需要承担的工作项，便于分阶段实现与评审。  
与工程规范的关系：调度、`loop()` 非阻塞、日志前缀等见 [`esp8266_embedded_standard.md`](esp8266_embedded_standard.md)。

---

## 1. 总目标（ESP8266 在系统中的职责）

| 职责 | 说明 |
|------|------|
| 网络接入 | 以 STA 连入现有 Wi‑Fi，获得局域网 IP，供浏览器或上位机访问 |
| HTTP 服务 | 提供静态页与 REST/类 REST 数据接口（读传感器/状态、下发控制意图等） |
| 串口侧 | 与 STM32 按约定协议收发、解析、组帧；与上层业务（缓存、Web 接口）衔接 |
| 资源形态 | 前端资源以内嵌字符串或 SPIFFS（及同类文件系统）形式提供 |
| 实时性 | 按需求选用轮询、WebSocket 或 SSE，在 RAM/CPU 约束下取舍 |

当前仓库已实现：**STA 凭据存储**（`WifiStaStore`）、**串口配网 CLI**（`WifiSerialProv`）、**入口调度**（`src/main.cpp`）。下文区分「已有基础」与「待扩展」。

---

## 2. WiFi（Station 模式）

### 2.1 ESP8266 需要做的事

1. **模式与连接**  
   - 使用 `WIFI_STA`（或 STA 为主、按需关闭 AP），上电或配置变更后发起连接。  
   - 处理断线重连（退避、最大重试、避免在 `loop()` 内长时间阻塞）。

2. **与现有代码衔接**  
   - 继续利用 `wifiSerialProvAutoloadAndConnect()` / `wifiSerialProvApplyStaConnect()` 等流程加载 Flash 中的 SSID/密码；服务器相关逻辑应在 **`WL_CONNECTED`** 之后再启动（或失败时降级、重试）。

3. **运维与可发现性（按需）**  
   - 串口或 Web 打印当前 IP、RSSI、连接状态（已有 `logWifiStatusIfChanged()` 思路可扩展）。  
   - 可选：mDNS（如 `http://xxx.local`）降低查 IP 成本。

4. **约束**  
   - 连接过程与 WiFi 栈回调内避免长耗时与大量日志；主循环保持轻量，符合工程规范中的 **`yield()` / 非阻塞`** 约定。

---

## 3. 异步 Web 服务器

### 3.1 ESP8266 需要做的事

1. **库与栈**  
   - 在 Arduino/ESP8266 上实现「异步」通常依赖 **ESPAsyncWebServer**（配合 **ESPAsyncTCP**）等库；在 `platformio.ini` 中声明依赖并固定版本，避免隐式升级破坏 API。

2. **生命周期**  
   - 在 WiFi 已连接（或 SoftAP 配网场景下 AP 已起）后 **`begin()`** 监听端口（默认 80 或自定义）。  
   - 处理 **404 / 方法不允许 / 体过大** 等基础错误响应，避免客户端挂死。

3. **路由分工**  
   - **静态或近静态**：`GET /`、`GET /style.css`、`GET /app.js` 等（见第 5 节资源来源）。  
   - **数据接口**：`GET /api/status`、`GET /api/telemetry`、按需 `POST /api/command` 等；返回 **JSON** 或紧凑二进制（与前端约定一致）。  
   - **CORS**：若仅局域网内嵌页面同源访问，可简化；若跨端口/跨设备则需按需设置头。

4. **异步语义下的实现要点**  
   - 处理器内 **避免** 长时间 `delay`、大块同步阻塞；需要慢操作时分段、缓存结果或由 STM32 侧异步完成后再读缓存。  
   - 大响应考虑 **分块** 或限制单次 JSON 体积，防止堆碎片与 OOM。

5. **安全与边界（轻量场景仍建议最小集）**  
   - 速率限制、简单 token 或局域网隔离策略按产品要求选做。  
   - 不在固件中硬编码长期密钥；敏感配置仍走 Flash/配网通道。

## 4. 串口接收与解析（与 STM32 的协议）

### 4.1 与现有「配网串口 CLI」的关系

- **`WifiSerialProv`**：面向人的 **文本命令**（SSID/PASS/SAVE 等），与 STM32 **二进制/定长帧协议** 可能冲突。  
- ESP8266 需要明确 **二选一或分时复用** 策略，例如：  
  - 专用引脚 **GPIO 切换**「配网模式 / 运行模式」；或  
  - 上电后短时间窗口仅接受 CLI，超时后只跑 STM32 协议；或  
  - **硬件双串口**（若板级支持）分别接调试口与 STM32。

### 4.2 ESP8266 需要做的事

1. **物理与参数**  
   - 波特率、8N1、流控与 STM32 一致；缓冲区大小满足 **最大帧长 + 余量**。

2. **非阻塞接收**  
   - 在 `loop()`（或等价轮询点）中 **`Serial.available()`** 逐字节或小批量读入环形缓冲；**不在** 此处长时间等待整帧（除非用独立状态机步进）。

3. **协议状态机**  
   - 按约定实现：帧头、长度、类型、载荷、校验（CRC/和校验等）、帧尾或定长对齐。  
   - 非法帧丢弃、同步字节对齐、超时复位解析状态，防止粘包/半包死锁。

4. **与 Web 层的数据桥**  
   - 将「最新有效测量/状态」写入 **RAM 中的结构化缓存**（带序号或时间戳）；Web 处理器只读该缓存，避免在 HTTP 回调里直接阻塞读 STM32。  
   - 下行命令：HTTP/WS 收到请求后 **入队**，由串口侧按序组帧发送，并记录发送结果/超时。

5. **错误与背压**  
   - 发送队列满、STM32 无应答时定义 **降级行为**（丢弃旧包、返回 503、串口打印错误码等）。

## 5. 网页文件存储（HTML/CSS/JS）

### 5.1 方案 A：内嵌字符串（PROGMEM / 字面量）

**ESP8266 需要做：**

- 将页面与脚本以 **`const char[] PROGMEM`** 或等效方式存放于 Flash，减少 RAM 占用。  
- 路由中 **`request->send_P(...)`**（异步库常见接口）或等价 API 指定 `text/html`、`application/javascript`、`text/css` 的 **Content-Type**。  
- 大页面拆分模块或 gzip 预压缩（若库支持），控制单次发送内存峰值。

**适用**：页面小、迭代少、无需现场换文件。

### 5.2 方案 B：SPIFFS / LittleFS

**ESP8266 需要做：**

- 分区或镜像中 **格式化并烧录文件系统**（PlatformIO `data/` 上传或自定义脚本）。  
- 启动时 **`SPIFFS.begin()` / `LittleFS.begin()`**，失败路径日志清晰。  
- 路由 **`request->send(SPIFFS, path, type)`** 或从文件读入再发送；注意路径与缓存头（按需 `Cache-Control`）。

**适用**：资源较多、希望不重新编译即可替换静态文件（仍受分区大小限制）。

### 5.3 选型提示

- RAM 紧张时优先 **Flash 驻留**（PROGMEM 或 FS）；避免在 RAM 中持有完整站点副本。  
- 与 **第 6 节** 推送方式配合：若用 SSE/WebSocket，HTML 中内联脚本需指向正确的 **ws/wss 或 sse URL**（同源或写明 IP）。

## 6. 实时数据推送

### 6.1 AJAX 轮询（最轻）

**ESP8266 需要做：**

- 提供 **`GET /api/...`** 返回 JSON（含时间戳或版本号），前端 `setInterval` 拉取。  
- 控制轮询间隔与 JSON 体积，减轻 CPU 与无线干扰。

**优点**：实现简单、与任意 HTTP 栈兼容。  
**缺点**：延迟 = 轮询周期；无效请求多。

### 6.2 Server-Sent Events（SSE）

**ESP8266 需要做：**

- 对 **`GET /events`（示例）** 返回 **`text/event-stream`**，保持连接并按 **`data: ...\n\n`** 格式推送。  
- 在异步服务器上确认 **长连接** 与 **TCP 超时** 行为；推送频率与串口/STM32 产出对齐，避免写 socket 过快。

**优点**：单向实时、浏览器原生 `EventSource`。  
**缺点**：ESP8266 上同时长连接数有限；需注意内存与栈。

### 6.3 WebSocket

**ESP8266 需要做：**

- 在 Async 栈上挂载 **WebSocket 端点**；握手后双向推送命令与状态。  
- 定义 **小消息 JSON** 或二进制子协议；心跳 ping/pong 防止中间设备断开 idle 连接。

**优点**：双向、实时性好。  
**缺点**：实现与调试成本高于轮询；连接与 RAM 占用高于 SSE。

### 6.4 选型建议（写在任务层）

| 场景 | 建议 |
|------|------|
| 状态刷新 ≥ 500 ms 可接受 | 轮询 + 紧凑 JSON |
| 仅服务器 → 浏览器推送、偶发数据 | SSE |
| 双向控制、低延迟、交互多 | WebSocket |

## 7. `setup()` / `loop()` 编排建议（任务顺序 checklist）

以下为 ESP8266 固件侧建议的 **初始化与主循环职责** 顺序，便于对照实现与 Code Review。

**`setup()`**

1. 串口、LED 等基础 IO。  
2. `wifiStaStoreBegin`、配网 CLI `wifiSerialProvBegin`（若仍保留）。  
3. WiFi STA 连接（已有 autoload/apply 流程）。  
4. （可选）文件系统挂载。  
5. STM32 串口协议解析器 **reset**。  
6. **WiFi 已连接后** 启动 Async WebServer（路由注册、WS/SSE 若启用）。  
7. 打印访问 URL（IP、端口、可选 mDNS）。

**`loop()`**

1. `wifiSerialProvPoll()`（若与 STM32 共用串口，按策略裁剪或关闭）。  
2. 串口接收 **非阻塞** 解析 → 更新共享状态缓存。  
3. 异步 Web 栈通常需 **`yield()`** 或库文档要求的周期性调用（以所选库 README 为准）。  
4. WiFi 重连状态机 tick。  
5. LED/看门狗喂狗等板级指示。

## 8. 与仓库文件的映射（便于落地）

| 能力 | 建议落点（可调整） |
|------|---------------------|
| STA 存储与连接触发 | 已有 `include/WifiStaStore`、`include/WifiSerialProv`；服务器启动条件在 `src/main.cpp` 或新建编排模块 |
| HTTP/WS/SSE | 新建模块（如 `include/WebApp/` 或 `lib/` 下独立库），避免与配网 CLI强耦合 |
| STM32 协议 | 新建 `Stm32Link` / `SerialFramer` 类模块，仅依赖 `Stream` 与环形缓冲 |
| 静态资源 | 同 Web 模块或独立 `assets_*.h` / `data/` |
